# speedtest — асинхронный замер скорости интернета

Скрипт многократно скачивает ресурс с сервера параллельно, подбирая оптимальное
число одновременных закачек, и считает:

- **среднее время запроса** (чтения тела);
- **суммарный объём** скачанных данных;
- **скорость** в `Мбит/с` (`Mbps`) — считается исходя из **битов в секунду** с точной
  арифметикой (`fractions.Fraction` → `decimal.Decimal`, без промежуточных
  округлений); `1 Мбит = 1 000 000 бит`.

## Требования

- Python 3.12+
- зависимости: `aiohttp`, `tenacity`

## Установка

```console
pip install -r requirements.txt
```

## Запуск

Запуск — из корня проекта (там, где лежит папка `speedtest/`):

```console
python -m speedtest
python -m speedtest https://example.com/big-image.jpg
python -m speedtest --requests 5 --concurrency 4 https://example.com/big-image.jpg
```

По умолчанию используется тестовый файл **ровно 100 000 000 байт** на CDN CacheFly (общий для бенчмарков):

```
http://cachefly.cachefly.net/100mb.test
```

Альтернатива — эталонный ресурс **ровно 50 000 000 байт** на стабильном CDN
Cloudflare (его же используют многие веб-спидтесты), но при высоком числе
скачиваний Cloudflare отдаёт `429` (ретраи учитывают `Retry-After`):

```
https://speed.cloudflare.com/__down?bytes=50000000
```

Пример с большой картинкой (~50 МБ) на Wikimedia Commons — работает, но при
параллельной нагрузке Wikimedia может отдавать `429` (ретраи отрабатывают):

```
https://upload.wikimedia.org/wikipedia/commons/a/a6/Cosmic_Calendar_%E2%80%93_deep_time_and_cosmic_history_as_one_year_%28time-lapse_and_annotations%3B_50MB_version%29.gif
```

Любой адрес можно передать как позиционный аргумент.

## Флаги

| Флаг | Описание | Дефолт |
| --- | --- | --- |
| `url` | адрес ресурса для скачивания | CacheFly 100 000 000 байт |
| `--requests`, `-n` | количество логических закачек | `10` |
| `--concurrency`, `-c` | стартовая параллельность для AIMD, `≥ 1` | `1` |
| `--attempts`, `-a` | максимум попыток на одну закачку (tenacity `stop_after_attempt`) | `3` |
| `--timeout` | таймаут «активности» чтения тела, сек | `30` |
| `--connect-timeout` | таймаут установки соединения (DNS/TCP/TLS), сек | `10` |
| `--verbose`, `-v` | подробный лог, включая ретраи и шаги волн | выкл |

## Как работает

### Онлайн-адаптация параллельности (AIMD)
Отдельной фазы калибровки нет — скрипт прямо по ходу замера подбирает число
одновременных закачек по правилу **AIMD** (Additive Increase / Multiplicative
Decrease, как в TCP), начиная с `--concurrency`:

- после каждой «волны» (группы одновременных закачек) считается пропускная
  способность `wave_tp = байты волны / span волны` и её сглаженное значение
  `ewma = 0.5·wave_tp + 0.5·ewma_prev`;
- **AI**: если пропускная способность выросла более чем на **10 %** относительно
  ewma — `cwnd += 1`;
- **деградация** (доля ошибок в волне `> 20 %` — обрывы, таймауты, `429` — или
  скорость упала более чем на **10 %**) — откат к **последнему известному
  оптимуму** `best_cwnd` (тот уровень, где была достигнута лучшая EWMA); если
  такого ещё не было — `cwnd = max(1, cwnd // 2)`;
- **мёртвая зона**: изменение скорости в пределах ±10 % — `cwnd` не меняется
  (гистерезис гасит шум канала);
- потолок `cwnd ≤ min(32, requests)`.

### Стабильная фаза и скорость
«Span волны» — это реальное время параллельной волны: **самая долгая** из
одновременных закачек (все стартуют вместе). Суммировать длительности
параллельных стримов нельзя — это даст среднюю скорость одного потока, а не
пропускную способность канала (спидтесты вроде Ookla меряют суммарную).
Скорость считается по **стабильной фазе** — волнам, начиная с первой, где AI
перестал срабатывать (достигнуто плато). Ранние «slow-start» волны с
малым числом соединений не занижают результат. Если плато не достигнуто (очень
малое `--requests`), берутся все сэмплы. Сэмплы после отката к `best_cwnd`
остаются в стабильной фазе — это известный хороший уровень.

Остаются честные расхождения со спидтестами: CDN может ограничивать сумму
соединений к одному серверу, а Ookla бьёт по своей инфраструктуре с десятков
ног параллельно.

### Таймауты и ретраи
- Таймауты через `aiohttp.ClientTimeout`: общий (`total`) не ограничивается —
  на медленных каналах 50 МБ может качаться дольше; защиту от «зависания»
  даёт `sock_read` (по `--timeout`).
- Ретраи на **временные** ошибки: сброс соединения, таймауты, HTTP `5xx`/`429`,
  частичная закачка (получено меньше `Content-Length`). Ожидание между
  попытками — экспоненциальный backoff с джиттером:
  `0.5 · 2ⁿ + random(0, 1)`, максимум 5 c;
  для `429`/`503` учитывается заголовок `Retry-After` — ждём столько,
  сколько просит сервер (не более 15 c за раз).
- HTTP `4xx` (кроме `408`/`429`) — постоянные ошибки, **не** ретраятся.
- Количество попыток на один запрос ограничено `--attempts`.

### Пример вывода

```
--- результаты ---
запрос |      объём | время, с | попытки | статус
     1 |    48.50 MiB |    2.140 |       1 | ok
   ...
среднее время запроса (стабильная фаза): 2.133 с
объём (стабильная фаза): 145.50 MiB (152,561,846 байт)
успешно: 3 / 3
параллельность: 1 → 6
стабильная фаза: с запроса #4
скорость: 178.68 Мбит/с
общее время выполнения: 8.240 с
```

### Ограничения
- Способность канала может упираться не только в него, но и в лимиты сервера,
  TLS, HTTP/1.1 или число допустимых соединений с хоста.
- Скорость считается по времени чтения тела успешной попытки (без времени
  ретраев и backoff).

## Структура проекта

```
speedtest/            # CLI-пакет
├── __init__.py       # публичный API и версия
├── __main__.py       # точка входа `python -m speedtest`
├── core.py           # скачивание, AIMD, расчёты (без I/O в консоль)
└── cli.py            # argparse, отчёт, запуск
tests/                # pytest: aimd, метрики, скачивание через локальный сервер
pyproject.toml        # конфиг ruff и pytest
```

## Тестирование

```console
python -m pytest -q
```

Тесты не ходят в интернет: HTTP-сценарии разворачиваются на локальном
`aiohttp.TestServer`.
